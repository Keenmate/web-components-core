Lifecycle

How a BlissElement is built once and activated many times: reinit() / update() for structure, connect() / disconnect() for live resources, the defer gate and the ready signal (SPEC §6.3), removedCallback(), destroy() (SPEC §6.5) and what happens when a hook throws. Every demo uses <core-demo-lifecycle>, a small element that reports each hook into the timeline under it (sequence number, then milliseconds since the button press).

LC01 · Build once, activate many

On first connect the base runs reinit() (the full build, from the merged this.config), then connect() (start listeners, observers, timers). On the microtask after that, the first build is announced as ready: the host gets the ready attribute and :state(ready), the ready event fires (its onReady twin is called with the same detail), isReady flips to true and whenReady() resolves. It's a microtask, not an animation frame, so a listener added on the line after append() still catches it, and a hidden tab doesn't hold it back. Later changes go through the input table: a change to an on:'reinit' input (label) rebuilds, a change to an on:'update' input (accent) is patched in place, and in a mixed batch the rebuild wins. ready is only ever announced once per element. 

const el = document.createElement('core-demo-lifecycle');
el.addEventListener('ready', (e) => log('ready event', e.detail.element === el));
el.onReady = (detail) => log('onReady twin');      // same detail object as the event
el.whenReady().then(() => log('whenReady() resolved'));
stage.append(el);            // reinit() → connect()   (synchronously, inside append)
el.isReady;                  // false — ready is announced on the next microtask
await Promise.resolve();
el.isReady;                  // true; el.hasAttribute('ready'); el.matches(':state(ready)')

el.label = 'Renamed';        // on:'reinit' → reinit() on the coalescing microtask
el.accent = 'green';         // on:'update' → update({ accent: 'green' })
el.batch(() => { el.label = 'B'; el.accent = 'amber'; });   // one reinit(), no update()

LC02 · defer / release()

Every component has a defer attribute (property shouldDefer). When it is set as the element first connects, the first build is held: no reinit(), no update(), no connect(). Inputs, callbacks and listeners set in the meantime just pile up. release(), or removing the defer attribute, then builds once with all of them in place. The order is defer → release → reinit → connect → ready. The gate is latched: once the first build has run, setting defer again holds nothing. While the gate is closed, whenSettled() stays pending until the release, so release first and await after. 

<!-- markup: hold the first build until the app has configured it -->
<core-demo-lifecycle id="card" defer></core-demo-lifecycle>

const el = document.getElementById('card');   // or: el.shouldDefer = true before append
el.label = 'Configured while held';            // stored — no reinit() yet
el.accent = 'amber';                           // stored — no update() either
el.release();                                  // ONE reinit() with both, then connect(), then ready
// el.removeAttribute('defer') does the same
el.shouldDefer = true;                         // latched: no effect after the first build

LC03 · DOM moves keep transient state

Reordering or re-parenting an element fires disconnect() → connect() and re-activates it without rebuilding. reinit() only runs on first connect or when an on:'reinit' input changes, so UI state that lives in the shadow DOM survives. Type something into the card and click its counter, then move it around. Config changed while the element is detached is held, and on reconnect it is applied before connect(). That counts as a real rebuild, so the typed text resets.

box Aneighbour
box B
boxB.append(el);                 // disconnect() → connect()   — no reinit(), state kept
boxA.insertBefore(el, neighbour); // reorder: the same

el.remove();
el.label = 'Changed while detached';  // held (whenSettled() resolves on the next connect)
boxA.append(el);                  // reinit() (the held change) → connect()

LC04 · removedCallback(): removed, not moved

disconnect() can't tell a move from a removal. removedCallback() can: it fires after disconnect() only if the element is still detached at the next animation frame (a macrotask when there is no rAF or the tab is hidden). A synchronous move, where disconnect and connect happen in the same task, cancels the check and never fires it. It's opt-in: the base schedules the check only for classes that override the hook (the demo card does). Use it for work that should survive a move but not a removal, such as aborting uploads. Re-adding afterwards is a fresh activation: connect() runs as usual, with no forced reinit(). 

class MyElement extends BlissElement {
  protected override removedCallback(): void {   // overriding it = opting in
    this.uploads.abortAll();                     // really gone, not just moved
  }
}

stage.removeChild(el); stage.append(el);   // same task → disconnect(), connect(); removedCallback never fires
el.remove();                               // disconnect() … next frame: removedCallback()

LC05 · destroy()

destroy() is the public final teardown. It runs disconnect() if the element is active, cancels a pending flush and the removal check, then calls the protected destroyCallback() hook, where a component releases what reinit() built. isDestroyed becomes true, and calling destroy() again does nothing. From then on the element is inert. Input writes are still stored but never applied (whenSettled() resolves at once), and re-inserting it into the DOM logs a warning (open the console) and never rebuilds. The ready state stays as it was. If you need it back, create a new element. 

el.destroy();       // disconnect() → destroyCallback()
el.isDestroyed;     // true
el.destroy();       // idempotent — no hooks run
el.label = 'x';     // stored (el.label === 'x'), never reaches reinit()
stage.append(el);   // console warning: "<core-demo-lifecycle> was destroyed — reconnecting it does nothing …"

LC06 · A throwing hook doesn't wedge the element

An error thrown by a hook is rethrown to whoever flushed: the caller of batch() / setAttributes() / flush(), or the browser's error reporting for a flush inside connectedCallback. The element still recovers. whenSettled() waiters resolve anyway, a failed reinit() is owed and retried on the next flush (any change, or a plain flush(); the owed rebuild beats an update()), and connect() only runs once a build has succeeded, so a structure that never got built is never activated. Arm the toggle, then trigger a rebuild. 

el.shouldThrowNextReinit = true;   // demo knob: the next reinit() throws once
try {
  el.batch(() => { el.label = 'Will fail'; });   // reinit() throws → rethrown here
} catch (err) { /* the old structure stays; el.label === 'Will fail' */ }
el.flush();                         // nothing pending, but the failed reinit() is owed → retried

// A failed FIRST build: no connect(), no ready — until a later flush succeeds
fresh.shouldThrowNextReinit = true;
stage.append(fresh);   // reinit() throws (reported to window 'error'), connect() skipped
fresh.flush();         // reinit() → connect() → ready

LC07 · API summary

MemberKindWhen / what
reinit()protected hookFull build. Runs on first connect and whenever a batch changes an on:'reinit' input. Reads this.config and gets no partial.
update(partial)protected hookIn-place patch with the changed on:'update' keys. Runs only when the batch has no reinit-level change.
connect()protected hookEvery connect, after any reinit()/update(), and only once a build has succeeded. Start live resources here.
disconnect()protected hookEvery disconnect (only if connect() ran). Stop what connect() started; keep the structure.
removedCallback()protected hook, opt-inAfter disconnect(), when the element is still detached at the next frame (macrotask fallback). Never fires on a synchronous move.
destroyCallback()protected hookCalled once by destroy(), after disconnect(). Release engines, stores and in-flight work.
destroy()methodFinal teardown. Idempotent; the element is inert afterwards and a reconnect warns.
isDestroyedgettertrue after destroy().
defer / shouldDeferattribute / propertyHolds the first build while set at first connect. Latched after the first build.
release()methodOpens the defer gate: one build with everything set so far (at the next connect when detached). Removing defer does the same.
ready attribute, :state(ready)host stateSet on the microtask after the first build + connect(). Once per element.
ready event / onReadyevent + twinFired at the same moment. The twin is called with the detail, then the event is dispatched (bubbles, not composed).
isReady / whenReady()getter / methodFlag and promise for the same moment. whenReady() never rejects: a failing first build keeps it pending.
whenSettled() / flush()methodsAwait the pending flush, or apply it synchronously now. flush() also retries an owed failed reinit().
batch(fn) / setAttributes(obj)methodsCoalesce several writes into one synchronous flush. A throwing hook is rethrown to the caller.
Keep connect() and disconnect() balanced
They can run many times per element (every DOM move), so whatever connect() starts, disconnect() must stop. Never tear structure down in disconnect(): the shadow DOM survives a move, and reinit() won't run again just because the element was reconnected.
