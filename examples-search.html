Search

The built-in search rules every component with a search box shares, from @keenmate/web-components-core/search: normalization (search-behavior), where the term matches (search-match), term preparation, and highlighting that follows the same rules. Pure functions; a component adds the per-item cache and the UI. See SPEC §12.11.

SE01 · Playground — behavior × match

The list is filtered and highlighted the way web-multiselect does it: every item's search value is normalized once per behavior (watch the counter — typing doesn't move it), the term goes through prepareSearchTerm, each item through matchesSearchTerm, and the label through findHighlightRanges + wrapRanges. Try ces, ČES, lodz, strasse, nad, town, haxkl324, or with regex: ^(Ústí|Nové).

matched: 0 values normalized so far: 0 ActiveSearchTerm: none
    regex is raw
    With match: 'regex' the pattern runs against the un-normalized value with no flags, so behavior stops mattering: ^ústí finds nothing, ^Ústí does. Type an unfinished pattern (^(Ústí|) — createRegexCompiler() keeps the last valid one, so the list doesn't flash empty.

    SE02 · normalizeSearchText — the three behaviors

    normalized strips combining marks after NFD and hand-folds the letters Unicode can't decompose (ł ø đ ð ħ ı ß→ss æ→ae œ→oe, final ς→σ). Every behavior applies NFC first, so the decomposed Zlín row (5 code units) equals the composed one (4). Export it to normalize a custom index exactly like built-in search.

    inputnormalizedcase-insensitiveexact

    SE03 · search-match — where the term must sit

    One term against a few values, every mode at once. A word is a run of letters and digits ([\p{L}\p{N}]), so - and / separate words and 324 starts a word in HA-324/56 but not in HA324 — try 324, ha, 56.

    SE04 · Highlight — why it returns { text, ranges }

    To mark Čes for the term ces, the label is folded one code point at a time with a map back to where each folded character came from. That works on the label's NFC form, so the ranges index into the NFC text — which findHighlightRanges returns alongside them. Below, the label is stored decomposed (Zlín) and the term is zli.

    input label
    returned text
    ranges
    ✅ wrapRanges(r.text, r.ranges)
    ❌ ranges applied to the input

    Markup is the caller's decision: wrapRanges takes open / close and an escape applied to every slice of the text (never to the markers). Pass an HTML escaper when labels are plain text; omit it when they are trusted HTML (web-multiselect's display values). 

    
            
    
        
    

        
        
        
        
    
            
    SE05 · Preparing the term — getSearchTermCallback
    
            
    
                Users type part numbers however they like: ha-324/56, ha 32456,
                HA32456. A component's getSearchTermCallback reaches core as
                prepare: return a RegExp and it is matched against the raw value (made
                stateless, so a g flag is harmless); return a string and it is used as-is, not normalized
                again; return an object and built-in search can't use it (onObjectTerm — the component
                warns; objects are for a custom searchCallback).
            
    
            
    
                
                
            
    
            
    
                ActiveSearchTerm: 
                
      
            
      
            
      const prepare = (term) => {
  const parts = term.split(/[^a-z0-9]+/i).filter(Boolean);
  return parts.length ? new RegExp(parts.join('[^a-z0-9]*'), 'i') : null;
};
prepareSearchTerm(typed, { behavior, match, regex, prepare });
      
        
      

        
        
        
        
      
            
      SE06 · Your own search — the searchCallback context
      
            
      
                Built-in search is strings only. Anything richer goes to the consumer's
                searchCallback(term, signal, { searchTerm, entries }) — the shape core's
                SearchCallbackContext fixes for every component. entries pairs each item with
                its search value (here an object, { title, zip }), is built on first access, and stays the
                same array until the items change, so an engine (FlexSearch, …) can key its index on
                it. Type a city or a postal code (335, 602 00).
            
      
            
      
                
                
            
      
            
      
                entries built: 0
                index (re)built: 0
                context.searchTerm: —
                
        
            
        
            
        // component side — what web-multiselect does
const context = { searchTerm, get entries() { return cachedEntries ??= Object.freeze(items.map(
  (item) => ({ item, searchValue: getSearchValueCallback(item) }))); } };
await searchCallback(term, signal, context);

// consumer side
getSearchValueCallback = (c) => ({ title: normalizeSearchText(c.city), zip: c.zip.replace(/[\s-]/g, '') });
getSearchTermCallback  = (t) => ({ text: normalizeSearchText(t.trim()), zip: t.replace(/[\s-]/g, '') });
searchCallback = (t, signal, { searchTerm, entries }) => {
  if (entries !== indexedFor) { index = buildIndex(entries); indexedFor = entries; } // once per item set
  return index.search(searchTerm);
};
        
        
        

        
        
        
        
        
            
        SE07 · API
        
            
        import {
  normalizeSearchText,                    // (text, behavior = 'normalized') → string
  findTextMatches, matchesText,           // (text, term, match) → ranges / boolean (prepared strings)
  findRegexMatches, statelessRegex,       // regex helpers
  NO_SEARCH_TERM, createRegexCompiler,    // { compile(pattern) → RegExp | null (last valid), reset() }
  prepareSearchTerm,                      // (term, { behavior, match, regex, prepare?, onObjectTerm? }) → ActiveSearchTerm
  matchesSearchTerm,                      // (term, match, prepared | () => prepared, raw | () => raw) → boolean
  findHighlightRanges,                    // (label, term, { behavior, match }) → { text, ranges }
  wrapRanges,                             // (text, ranges, { open?, close?, escape? }) → string
} from '@keenmate/web-components-core/search';
