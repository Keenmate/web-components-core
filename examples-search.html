    SE02 · normalizeSearchText — the three behaviors

    normalized decomposes with NFKD (ligatures and full-width forms fold too: ﬁ→fi), strips combining marks only after Latin, Greek and Cyrillic letters (a Devanagari vowel sign or a kana dakuten stays), lowercases, and hand-folds the letters Unicode can't decompose (ł ø đ ð ħ ı ŧ ŀ ß→ss æ→ae œ→oe þ→th ĳ→ij, final ς→σ). case-insensitive lowercases and also folds ß→ss and İ→i. Every behavior applies NFC first, so the decomposed Zlín row (5 code units) equals the composed one (4). Export it to normalize a custom index exactly like built-in search.

    SE03 · search-match — where the term must sit

    One term against a few values, every mode at once. A word is a run of letters, digits and combining marks ([\p{L}\p{N}\p{M}]), so - and / separate words and 324 starts a word in HA-324/56 but not in HA324 — try 324, ha, 56.

    SE04 · Highlight — why it returns { text, ranges }

    To mark Čes for the term ces, the label is folded one code point at a time with a map back to where each folded character came from. That works on the label's NFC form, so the ranges index into the NFC text — which findHighlightRanges returns alongside them. Below, the label is stored decomposed (Zlín) and the term is zli.

    input label
    returned text
    ranges
    ✅ wrapRanges(r.text, r.ranges)
    ❌ ranges applied to the input

    wrapRanges takes open / close and an escape applied to every slice of the text (never to the markers). escape defaults to escapeHtml, so a plain-text label comes out as safe HTML. A label that is already trusted HTML (web-multiselect's display values) goes through highlightHtml instead: tags are kept and never marked, entities are never split.     SE05 · Preparing the term — getSearchTermCallback
    
            
    
                Users type part numbers however they like: ha-324/56, ha 32456,
                HA32456. The consumer's getSearchTermCallback gets one context object,
                { term, target, behavior, match }. For built-in search the component binds it to
                target: 'internal' and hands prepareSearchTerm a plain (term) => ….
                Return a RegExp and it is matched against the raw value (made stateless, so a g
                flag is harmless); return a string and it is used as-is, not normalized again; return an object and
                built-in search can't use it (onObjectTerm — the component warns; objects are for
                target: 'callback', the consumer's own searchCallback).
            
    
            
    
                
                
            
    
            
    
                ActiveSearchTerm: 
                
      
            
      
            
      // consumer side
el.getSearchTermCallback = ({ term, target, behavior, match }) => {
  const parts = term.split(/[^a-z0-9]+/i).filter(Boolean);
  return parts.length ? new RegExp(parts.join('[^a-z0-9]*'), 'i') : null;
};

// component side — bind the context, pass core a (term) => …
const cb = this.getSearchTermCallback;
prepareSearchTerm(typed, {
  behavior, match, regex,
  getSearchTermCallback: cb ? (term) => cb({ term, target: 'internal', behavior, match }) : undefined,
});
      
        
      

        
        
        
        
      
            
      SE06 · Your own search — the searchCallback context
      
            
      
                Built-in search is strings only. Anything richer goes to the consumer's
                searchCallback(ctx) — one argument, { term, signal, entries }, the shape core's
                SearchCallbackContext fixes for every component (a component adds its
                controller / element). term is what
                getSearchTermCallback returned for target: 'callback' (here an object), else
                the typed text. signal aborts when a newer search starts. entries pairs each
                record with its search value, { data, searchValue } (here searchValue is
                { title, zip }). It is built on first access and stays the same array until
                the items change, so an engine (FlexSearch, …) can key its index on it.
                Type a city or a postal code (335, 602 00).

        // component side — what web-multiselect does
const term = getSearchTermCallback
  ? getSearchTermCallback({ term: typed, target: 'callback', behavior, match })
  : typed;
const ctx = { term, signal, get entries() { return cachedEntries ??= Object.freeze(items.map(
  (data) => ({ data, searchValue: getSearchValueCallback(data) }))); } };
await searchCallback(ctx);

// consumer side
getSearchValueCallback = (c) => ({ title: normalizeSearchText(c.city), zip: c.zip.replace(/[\s-]/g, '') });
getSearchTermCallback  = ({ term }) => ({ text: normalizeSearchText(term.trim()), zip: term.replace(/[\s-]/g, '') });
searchCallback = ({ term, signal, entries }) => {
  if (entries !== indexedFor) { index = buildIndex(entries); indexedFor = entries; } // once per item set
  return index.search(term);
};
        
        
        

        
        
        
        
        
            
        SE07 · API
        
            
        import {
  normalizeSearchText,                    // (text, behavior = 'normalized') → string
  findTextMatches, matchesText,           // (text, term, match) → ranges / boolean (prepared strings)
  findRegexMatches, statelessRegex,       // regex helpers
  NO_SEARCH_TERM, createRegexCompiler,    // { compile(pattern) → RegExp | null (last valid), reset() }

  matchesSearchTerm,                      // (term, match, prepared | () => prepared, raw | () => raw) → boolean
  findHighlightRanges,                    // (label, term, { behavior, match }) → { text, ranges }
  wrapRanges,                             // (text, ranges, { open?, close?, escape? }) → string; escape defaults to escapeHtml
  highlightHtml,                          // (trustedHtml, term, { behavior, match, open?, close? }) → string
  escapeHtml,                             // (text) → text with & < > " ' escaped
} from '@keenmate/web-components-core/search';
