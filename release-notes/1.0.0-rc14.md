# Web Components Core 1.0.0-rc14 — Release Notes

**Released:** 2026-10-22 · **Pre-release** (`npm install @keenmate/web-components-core@rc`)

rc14 adds one module: **`@keenmate/web-components-core/search`**, the built-in search rules that
web-multiselect 2.6.0-rc02 shipped, moved to core so every KeenMate component with a search box
normalizes, matches and highlights the same way. `search-behavior` and `search-match` will mean
the same thing in multiselect, treeview and later grid / dropzone filters. Nothing existing
changed, so upgrading from rc13 needs no action.

The exhaustive, per-change list is in [`CHANGELOG.md`](https://github.com/KeenMate/web-components-core/blob/v1.0.0-rc14/CHANGELOG.md#100-rc14---2026-10-22);
this document covers the highlights and how a component uses the module.

## Upgrade checklist

**Everyone**

- [ ] Nothing. No existing export, attribute, event or behaviour changed.

**Component authors adopting `/search`**

- [ ] Import from `@keenmate/web-components-core/search` and drop the component-local copy of
      normalization / matching / highlight code.
- [ ] Keep the per-item cache in the component: normalize each item's search value **once**
      with the current behavior and pass it to `matchesSearchTerm` — not on every keystroke.
- [ ] Create **one** `createRegexCompiler()` per component instance.
- [ ] Render the `text` returned by `findHighlightRanges`, never the original label
      ([why](#highlighting)).

## New features — search

### Two independent axes

| Axis | Type | Decides |
|---|---|---|
| `search-behavior` | `SearchBehavior` | how text is normalized — applied to the item values **and** the term |
| `search-match` | `SearchMatch` | where in the value the term must sit |

### Normalization — `normalizeSearchText(text, behavior?)`

| Behavior | Ignores | Example |
|---|---|---|
| `normalized` (default) | case and diacritics; folds `ł ø đ ð ħ ı ß æ œ ς` | `ces` → `Český`, `strasse` → `Straße`, `muller` → `Müller` |
| `case-insensitive` | case only | `čes` → `Český`, `ces` does not |
| `exact` | nothing | case- and diacritic-sensitive |

Every mode NFC-normalizes first, so decomposed data (`C` + combining caron) matches its
precomposed form.

### Match modes

| Match | The term must be… |
|---|---|
| `contains` (default) | anywhere |
| `equals` | the whole value — codes: `haxkl324` finds `HAxKL324`, not `HAxKL3245` |
| `starts-with` / `ends-with` | at the start / end of the whole value |
| `word-starts-with` / `word-ends-with` | at the start / end of any word (a word is a run of `[\p{L}\p{N}]`) |
| `regex` | a regular expression, tested against the **raw** value — no flags, no normalization |

Lower-level helpers: `findTextMatches` (ranges) / `matchesText` (boolean, early exit) for the text
modes, `findRegexMatches`, and `statelessRegex` (strips `g` / `y` so `.test()` doesn't carry
`lastIndex` between items).

### Preparing and testing a term

```ts
import {
  createRegexCompiler, matchesSearchTerm, normalizeSearchText, prepareSearchTerm,
} from '@keenmate/web-components-core/search';

const behavior = 'normalized', match = 'word-starts-with';
const prepared = items.map((i) => normalizeSearchText(i.label, behavior)); // once per item
const regex = createRegexCompiler();                                        // once per instance

const term = prepareSearchTerm(typed, { behavior, match, regex });
const hits = items.filter((i, n) => matchesSearchTerm(term, match, prepared[n], i.label));
```

- `prepareSearchTerm` returns an `ActiveSearchTerm`: `{ kind: 'none' }` (empty term, everything
  matches; also exported as `NO_SEARCH_TERM`), `{ kind: 'text', text }`, or
  `{ kind: 'regex', re }`.
- **Half-typed regexes don't blank the list.** An invalid pattern (`^(Ústí|`) returns the
  compiler's last valid RegExp; `regex.reset()` forgets it.
- **Custom term preparation.** Pass `prepare` (the component's bound `getSearchTermCallback`):
  a returned RegExp is matched raw, a string is used as-is (**not** normalized again), and an
  object goes to `onObjectTerm`, since built-in search can't use it. The examples page shows a
  part-number preparer.
- `matchesSearchTerm` accepts the prepared and raw values **or functions returning them**, so a
  value is computed only when the current term needs it.

### Highlighting

```ts
const { text, ranges } = findHighlightRanges('Český Krumlov', term, { behavior, match });
wrapRanges(text, ranges, { escape });   // 'Český <mark>Kru</mark>mlov'
```

- Highlighting follows the matching rules exactly: `ces` marks `Čes` in `Český`, word modes mark
  only word starts / ends, `ß` is marked whole by `ss`, and combining marks after a match stay
  inside it.
- **Render the returned `text`.** For text terms it is the NFC form of the label, and the ranges
  index into it. On decomposed input the indices differ from the original string.
- `wrapRanges(text, ranges, { open, close, escape })` defaults to `<mark>…</mark>`. Pass an HTML
  escaper when the label is plain text; `escape` is applied to the text slices, never to
  `open` / `close`.

### The shared `searchCallback` convention

Types for the contract every component's custom search follows —
`searchCallback(term, signal, context)`:

| Type | Is |
|---|---|
| `SearchCallbackContext<T>` | `{ searchTerm, entries }` — the third argument |
| `SearchEntry<T>` | `{ item, searchValue }` — one item with its raw search value |
| `SearchTermContext` | `{ target: 'internal' \| 'callback', behavior, match }` — passed to `getSearchTermCallback` |
| `PreparedSearchTerm` | what `getSearchTermCallback` may return: string, RegExp, object, or empty |

`entries` is built on first access, and the array keeps the **same reference** until the items
change, so a search engine (Fuse, MiniSearch, …) can key its index on it.

Also exported: `SearchBehavior`, `SearchMatch`, `ActiveSearchTerm`, `SearchRange`,
`HighlightResult`, `RegexCompiler`, `PrepareSearchTermOptions`, `WrapRangesOptions`.
