# Web Components Core 1.0.0-rc17 — Release Notes

**Released:** 2026-11-02 · **Pre-release** (`npm install @keenmate/web-components-core@rc`)

rc17 adds the **motion level**: one switch for how much every component animates (`none`,
`snappy`, `smooth`, or `auto`) per element, per section or for the whole page. It guarantees the
OS reduced-motion setting on every page, with or without base-css-variables. It also renames one
option of rc16's `scrollIntoContainer()`.

**Upgrading needs action only if you already call `scrollIntoContainer(…, { revealContainer })`**
(rename the key). Pages and components get the motion level automatically.

The exhaustive, per-change list is in [`CHANGELOG.md`](https://github.com/KeenMate/web-components-core/blob/v1.0.0-rc17/CHANGELOG.md#100-rc17---2026-11-02);
this document is the upgrade guide and the highlights.

## Upgrade checklist

**Component authors**

- [ ] `scrollIntoContainer(el, { revealContainer })` → `{ shouldRevealContainer }` ([details](#revealcontainer--shouldrevealcontainer)).
- [ ] Animate only through your `--<prefix>-transition-*` tokens chained to `--base-duration-*`, and
      scroll through `--<prefix>-scroll-behavior`. A hard-coded `transition: 0.2s` ignores the motion
      level ([details](#motion-level)).
- [ ] Optional: your own `@media (prefers-reduced-motion)` block is no longer required; core guarantees
      it. Keeping it is harmless.

**Pages using components**

- [ ] Nothing. To use the new switch: `motion="none"` on an element, `data-motion="snappy"` on a
      section, or `window.components.motion = 'none'`.

## Breaking changes

### `revealContainer` → `shouldRevealContainer`

The rc16 option follows the boolean naming rule (`is` / `should` / `has` / `can`). Same behaviour:

```ts
// rc16
scrollIntoContainer(hit, { block: 'center', revealContainer: true });
// rc17
scrollIntoContainer(hit, { block: 'center', shouldRevealContainer: true });
```

## New features

### Motion level

| Where | How |
|---|---|
| one element | `<web-multiselect motion="none">` / `el.motion = 'snappy'` (reflects; `setAttributes({ motion })`) |
| the whole page | `window.components.motion = 'none'`, for every element left on `auto` |
| a section / the page in markup | `data-motion="smooth"` on any element: everything inside follows |

| Level | `--base-duration-fast / -normal / -medium / -slow` | `--base-scroll-behavior` |
|---|---|---|
| `none` | `0s` ×4 | `auto` (instant) |
| `snappy` | `0.05s / 0.08s / 0.12s / 0.15s` | `smooth` |
| `smooth` | `0.15s / 0.25s / 0.35s / 0.45s` | `smooth` |
| `auto` (default) | nothing set: inherited from a section or the page, else the component's own defaults | |

**How it works.** Core writes the resolved level (the element's own, else the page's) to
`data-motion` on the element. It also adds one small shared stylesheet to the document, and to any
shadow root a component lives in, that maps `[data-motion]` onto the shared speed tokens. Components
already animate through those tokens, so they follow without code of their own, and `data-motion` on
a section works even on pages without base-css-variables. Every level sets the scroll behaviour too,
so a level nested inside another follows the nearest one for both speed and scrolling.

**Precedence:** the OS reduced-motion setting > the element's own level > the nearest
`data-motion` ancestor > base-css-variables' defaults > the component's fallbacks. **The OS setting
always wins**, even over `motion="smooth"`: it's the user's accessibility choice.

New exports: `MOTION_VALUES`, `MOTION_PRESETS`, `MOTION_CSS`, `MOTION_ATTRIBUTE`,
`MOTION_DATA_ATTRIBUTE`, `adoptMotionStyles`, `getPageMotion`, `observePageMotion`, type `Motion`.
The CEM plugin documents `motion` on every component. See **SPEC §12.16**.

## Visible changes without a migration

- Every component now carries a `motion` attribute / property, and gets `data-motion` when a level
  applies.
- Under the OS reduced-motion setting, core zeroes the speed tokens on every page, even without
  base-css-variables. Components that didn't handle reduced motion themselves now stop animating
  there.
- A `[data-motion]` stylesheet is added to the document (and to the shadow roots that host
  components). It affects only elements carrying `data-motion`, plus `:root` under reduced motion.

## Documentation

- **`examples-motion.html`** (new, card 14): the four levels side by side with the measured
  durations, the page-wide switch and a section-level `data-motion`, an element keeping its own
  level, and a note showing whether the browser currently reports reduced motion.
- **SPEC §12.16** documents the mechanism, the presets, the precedence and the component contract.
- Real-browser e2e (`e2e/motion.spec.ts` on `test/motion.html`): computed durations per level,
  nesting, a component inside another's shadow root, and the OS setting beating `smooth`. A unit
  test keeps core's presets equal to base-css-variables'.
