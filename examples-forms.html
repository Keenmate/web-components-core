Forms

What a form-associated BlissElement (static formAssociated = true) gets from core: el.form and the protected internals, the disabled state (the reflected isDisabled input + <fieldset disabled>, SPEC §6.4) and the constraint-validation API with setFormatError() (SPEC §6.6). The demos use <core-demo-field>, a small quantity field that follows the KeenMate submission convention: its value is submitted by a light-DOM hidden <input> it renders as its own child — the host never calls internals.setFormValue().

FO01 · Form association and el.form

A form-associated custom element takes part in its form, but unlike a native control it gets no .form property for free: the browser keeps the association inside ElementInternals. Core re-exposes it as el.form (read through the lazily attached, protected internals — a subclass must never call attachInternals() itself). Unlike closest('form'), it honours the form="id" attribute, so event.target.form resolves for frameworks that route by it (Phoenix LiveView's phx-change). The submitted data comes from the hidden <input name> each field renders in its light DOM; the field outside the form copies its form attribute onto that input (component code). Core implements no formResetCallback — the demo field has its own, returning to its value attribute like a native input.

<form id="do-fo01-form">
outside the form, form="do-fo01-form" 
class CoreDemoField extends BlissElement {
  static formAssociated = true;               // el.form, formDisabledCallback, validity API
  reinit() {
    this.#hidden ??= Object.assign(document.createElement('input'), { type: 'hidden' });
    this.#hidden.name = this.config.name;     // the light-DOM input is what the form submits
    this.append(this.#hidden);
  }
  formResetCallback() {                       // the component's own — core has none
    this.value = this.getAttribute('value') ?? '';
  }
}

el.form;                                      // <form id="do-fo01-form"> — also via form="do-fo01-form"
el.closest('form');                           // null for the outside field
form.addEventListener('change', (e) => e.target.form);   // resolves like a native input
[...new FormData(form)];                      // [['qty','3'], ['note','hi'], ['extra','7']]

FO02 · Disabled: isDisabled and <fieldset disabled>

Two sources disable a form-associated host, and core merges them once in formDisabledCallback (components don't implement it). The isDisabled input (attribute disabled) must reflect: the browser treats the host's own disabled attribute as disabling it, so a non-reflecting input set back to false by property would leave the element disabled — the input-table check warns about that. A disabled ancestor <fieldset> is the other source. It never writes el.isDisabled; the protected isFormDisabled reports the fieldset side only, and isEffectivelyDisabled (input OR fieldset) is the state to apply. Read it in reinit(), and apply flips in the disabledChanged(isDisabled) hook, which fires only when the effective state actually changes on a built element (not for a rebuild). The native :disabled pseudo-class matches either way. Note that the demo disables its light-DOM hidden input itself in that hook: the host's own disabled attribute doesn't disable children.

Shipping (fieldset) 
static inputs = [
  { configKey: 'isDisabled', attribute: 'disabled', converter: toBool('presence'),
    default: false, shouldReflect: true },             // must reflect (SPEC §6.4)
];
reinit()  { this.#applyDisabled(this.isEffectivelyDisabled); }   // input OR fieldset
update(p) { /* ignore p.isDisabled */ }
disabledChanged(isDisabled) { this.#applyDisabled(isDisabled); } // flips on a built element

fieldset.disabled = true;   // el.isDisabled stays false; isFormDisabled true → disabledChanged(true)
el.isDisabled = true;       // reflects disabled="" → still disabled → no second disabledChanged

FO03 · Validity and setFormatError()

A form-associated class gets the standard constraint-validation API, read through internals: validity, validationMessage, willValidate, checkValidity() (fires the cancelable invalid event when invalid) and reportValidity() (also shows the browser's bubble). The protected setFormatError(error, message?, anchor?) marks the host invalid (customError) when the component could not produce a value. The message is message, else the error's own message, else "The value is invalid."; anchor, a descendant such as the visible input, positions the bubble (an anchor the browser rejects is dropped with a warning). null clears it, and clears all validity flags. While invalid, :invalid matches and the form fires invalid instead of submit — unless it is <form novalidate>. Type something that isn't a whole number (abc) into either field, then submit both.

#produceValue() {
  const raw = this.config.value.trim();
  if (raw === '' || /^-?\d+$/.test(raw)) {
    this.#hidden.value = raw;
    this.setFormatError(null);                     // valid again
  } else {
    this.#hidden.value = '';                       // submit '' — never a half-parsed value
    this.setFormatError(new Error(`"${raw}" is not a whole number`), undefined, this.#input);
  }
}

el.validationMessage;      // '"abc" is not a whole number'
el.matches(':invalid');    // true
form.requestSubmit();      // 'invalid' fires on el, no 'submit' (a novalidate form submits)

What core leaves to the component
Submission (KeenMate components render light-DOM hidden inputs named by name, with a value-format, rather than internals.setFormValue()), formResetCallback, formStateRestoreCallback, and any validity constraint other than the format error (set through internals directly — setFormatError(null) clears every flag).
