IA01 · emit(): typed events and their twins

A component declares the events it fires in static events (a bare name, or an object like { name: 'ping-wide', composed: true } when one event needs its own dispatch settings) and fires them with this.emit(name, detail).

Every event has a twin: a property callback named on<Name> (ping → el.onPing, ping-wide → el.onPingWide). It's the alternative to addEventListener, handy where a framework binds properties more easily than listeners. emit() calls the twin first, with the same detail object the listeners get. If the twin throws, the error is logged and the event still fires.

The detail carries your data plus two references: controller (the component's public API from createController()) and element (the host). Both are hidden from Object.keys and JSON.stringify, so logging or serializing the detail shows only the data, yet const { controller, element } = e.detail still works. Extra visible fields come from eventContext() (here emittedBy). The object you passed to emit() is copied, never modified.

Events bubble, but by default they do not leave a shadow root (composed: false). If a component uses another component inside, the inner one's events stay inside, so page code listening for the outer component's events never receives the inner one's by accident. ping-wide opts out with composed: true.

Try it. Each place an event reaches flashes in order, and the whole card flashes when it reaches document. On the light-DOM emitter, ping and ping-wide take the same path, because there is no shadow boundary to cross. On the nested emitter, ping stops at the shell's shadow root, while ping-wide reaches the shell host and the document, reported with the shell as its target (the browser retargets it).

type Events = { ping: { count: number }; 'ping-wide': { count: number } };

class Emitter extends BlissElement<Events, EmitterController> {
  static events = ['ping', { name: 'ping-wide', composed: true }];
  protected createController() { return { fire: (n) => this.fire(n), get count() { … } }; }
  protected eventContext() { return { emittedBy: this.id }; }   // enumerable extra
  fire(name = 'ping') { this.emit(name, { count: ++this.count }); }
}

el.onPing = (detail) => { … };                       // twin: called FIRST, with the detail
el.addEventListener('ping', (e) => e.detail);        // same object as the twin got
el.on('ping', (e) => { … });                         // typed addEventListener, returns unsubscribe
const { controller, element, count } = e.detail;     // destructuring works
JSON.stringify(e.detail);                            // '{"count":1,"emittedBy":"…"}' — no controller/element

IA02 · before*Callback: one contract

A before-callback lets the page veto or change an action before the component does it. Here beforeRenameCallback runs before an item is renamed and beforeSelectCallback before one is selected. Every component's before-callbacks follow the same contract.

The hook gets one ctx describing what is about to happen (plus the hidden element / controller from IA01) and answers with its return value: false cancels and nothing happens; undefined (or no return) goes ahead unchanged; any other value, even null, goes ahead with that value instead. What the value means is up to each hook: here a replacement label, or a different id to select. The hook may be async (return a promise). A hook that throws counts as a cancel and is logged as an error.

Components run the hook through a core helper. runBeforeCallback(fn, ctx, name) always waits (it returns a promise), which suits rename, an async method anyway. runBeforeCallbackEager answers right away when the hook is synchronous and returns a promise only for an async hook. Select uses it, so with a sync hook (or none) el.select('beta') has already selected by the time it returns: the very next line reads el.selectedId === 'beta'. With an async hook the selection lands later.

Try it. Pick a return value for each hook, then use the buttons below or the select / rename buttons in each row. A rename proposes "Alpha #1", "#2", …; the log shows what the hook answered, the final label and rename() resolved true / false. For select, watch the line select() returned — el.selectedId = …: with a sync hook it already shows the new id, with an async one it still shows the old id and the selected line follows about 400 ms later. 

el.beforeRenameCallback = (ctx) => {        // ctx: { id, oldLabel, newLabel } + element / controller
  if (ctx.newLabel.length > 20) return false;  // reject
  return ctx.newLabel.trim();                  // replace — or return nothing to continue unchanged
};

// inside the component
const r = await runBeforeCallback(this.config.beforeRenameCallback, this.withContext(ctx), 'beforeRenameCallback');
if (r.isRejected) return;
const label = r.hasValue ? r.value : ctx.newLabel;

const s = runBeforeCallbackEager(this.config.beforeSelectCallback, ctx, 'beforeSelectCallback');
if (s instanceof Promise) s.then(apply);   // async hook: wait
else apply(s);                             // sync hook (or unset): same tick

IA03 · /actions: clickable items and the action event

/actions is how a component draws clickable things the page configures (toolbar buttons, action buttons, menu items) and reports every click through one action event. The demo toolbar gets its buttons from el.items (code below).

Each item is an ActionItem: either a built-in action the component knows (add, reset, fail here) or your own id (hello, bold), plus text, tooltip, isDisabled, isDanger, isToggled, isVisible and more. Any of these can also be a callback (getIsToggledCallback(ctx), …) that is asked on every render and wins over the fixed value. The component adds its own rules: Reset is disabled while the count is 0. Bold is a toggle, its aria-pressed follows isBold. A sixth item, Hidden, has isVisible: false, so it isn't drawn.

A click runs runAction(), always in this order: beforeActionCallback (false cancels the whole click, the IA02 contract) → the item's own onClick → the built-in behaviour (add increments the count) → the action event and its onAction twin. The event comes last, as a notification: the listener already sees the new state, so el.count is updated while detail.count still holds the value at click time. If onClick or the built-in throws, the error is logged and the event still fires. While a click is still running (for example, waiting for an async beforeActionCallback), its button is aria-busy and further clicks on it are ignored.

Plain HTML inside the component joins in too: a button with data-action / data-id goes through the same steps, and its other data-* attributes arrive as detail.dataset. detail.source says where the click came from: "toolbar" for the drawn buttons, "markup" for the HTML one. That is a name this demo chose; source accepts any string.

Try it. The button pings when its action event arrives. Click +1 and compare detail.count (at click) with el.count (now) in the action event line. Tick the checkbox and click Say hello, or click Broken built-in: the error is logged and the event still fires. Click Markup button for source "markup" and dataset {"row":"42"}. Set beforeActionCallback to returns false and clicks do nothing; set it to async: continue after 800 ms and double-click +1: the second click logs item is busy. 

let isBold = false;
el.items = [
  { action: 'add', text: '+1', onClick: (d) => log('onClick', d.count) },
  'reset',                                             // string shorthand for { action: 'reset' }
  { id: 'hello', text: 'Say hello', onClick: () => { … } },
  { id: 'bold', text: 'Bold', getIsToggledCallback: () => isBold, onClick: () => { isBold = !isBold; } },
  { action: 'fail', text: 'Broken built-in', isDanger: true },
];
el.beforeActionCallback = (detail) => detail.action === 'reset' ? confirm('Reset?') : undefined;
el.addEventListener('action', (e) => {
  e.detail.action; e.detail.id; e.detail.source; e.detail.dataset;  // + surface context (count)
  el.count;                                         // already updated by the built-in
});

// inside the component, per click:
await runAction({
  detail: this.withContext({ count, action, id, item, source: 'toolbar', sourceEvent, triggerElement, dataset }),
  beforeActionCallback: this.config.beforeActionCallback,
  runBuiltIn: (d) => this.#runBuiltIn(d),
  emitAction: (d) => this.emit('action', d),
});

IA04 · /menu: context and dropdown menus

/menu gives components one shared context menu and dropdown menu. openMenu(entries, ctx, opts) draws a list of /actions items (IA03's ActionItem, plus submenus and dividers) for one context: here the file that was right-clicked, or { file: null } for the Actions dropdown. at says where it opens: a point (the mouse position) or an element to drop down from (the button).

What the demo menus show:

  • Submenus. Share has fixed children (with a nested More). Move to loads its children on demand through getChildrenCallback: a … row shows for 700 ms, then the folders.
  • Dividers. createMenuDivider() draws a plain line, createMenuDivider('Danger zone') a labelled one. A divider left at the end of a menu, or two in a row, is removed: the dropdown lists two dividers around a hidden item, and you see one.
  • Hidden and disabled. The dropdown's Never shown item has isVisible: false. Archive is disabled on the locked file (contract.docx) through getIsDisabledCallback.
  • Toggle. Pinned is a checkbox item (menuitemcheckbox) with shouldCloseOnClick: false, so the menu stays open and you see the check flip.
  • Shortcuts. While a menu is open, an item's shortcut key runs it (O, F2, Delete; N, H in the dropdown).

Picking an item goes through the component's runAction(), the same order as IA03: beforeActionCallback → onClick → built-in → action event. An item without a submenu closes the menu first (onClose reason 'action') and then runs, so when beforeActionCallback cancels, the menu is already gone. The menu also closes on a click outside, Esc, Tab, the window losing focus, and any scroll outside it; onClose gets the reason. That is why the timeline below has no height limit: scrolling it would close the menu.

The menu is themed with CSS variables. --km-menu-* on :root styles every menu on the page. A component can also map a variable of its own onto the private --_km-menu-* layer: here --dfm-menu-bg styles only this file list's menus. The two theme checkboxes switch each one on; tick one, then open a menu (the click on the checkbox closes an open menu, like any click outside).

Try it. Right-click report.pdf and click Pinned: the menu stays open, the check flips and the row gets a pinned tag. Hover Move to to watch it load. Right-click contract.docx: Archive is greyed out. Tick the beforeActionCallback box and pick Delete: the menu closes, the log shows → false and the file stays. Actions ▾ opens the dropdown. From the keyboard, focus a file and press Shift+F10, then the arrows or a shortcut (F2 renames). A row an action changed pings.

Callback or event?
A name ending in Callback is a hook whose return value matters (it vetoes, adjusts or supplies something) and may be async. An event (no suffix, kebab-case, never a composed native name such as click) is a fire-and-forget notification, and its on<Name> twin's return value is ignored.
