The null-clear contract

How BlissElement hands a cleared input to an engine — null means “reset”, undefined means “leave alone”. Assemble the engine config with this.engineConfig(exclude) (→ collectEngineConfig) so the clear signal survives. See SPEC §6.1.

NC01 · Two absent-sentinels, never conflated

The partial an engine receives carries two distinct kinds of “absent”:

The rule
undefined = not in this batch — the key didn't change, leave the engine's current value alone (this is what the if (updates.x !== undefined) guard skips).
null = explicitly cleared — a real value, produced when a nullable input is emptied (removeAttribute or el.prop = null). It is the input's declared unset state, so a set→clear round-trip returns the field to how it was born.

NC02 · collectEngineConfig preserves null

The pure assembler, driven directly (no component). Set a value, then clear it, and watch the assembled config: the key stays present with null — it is not dropped. Compare with the old hand-rolled “delete every null” loop.

NC03 · The bug & the fix, live

A real BlissElement (<nullclear-card>) driving a stub engine with the genuine !== undefined merge. Row 2 is focused; its highlight class comes from the focused-node-class input, falling back to a built-in default (nc-focus-default, the blue bar). Set a custom class, then Clear it:

  • preserve (engineConfig): clearing reverts to the blue default. ✅
  • strip (old loop): clearing is a silent no-op — the custom class sticks. 🐛

NC04 · API summary

import { collectEngineConfig } from '@keenmate/web-components-core';

// Component side — assemble the config to hand your engine:
protected override update(partial = {}) {
  const cfg = this.engineConfig(NON_ENGINE_KEYS); // shallow copy, nulls PRESERVED
  Object.assign(cfg, partial);                    // partial already carries null
  this.#engine.update(cfg);
}

// Engine side — treat null as a real value, per field:
if (updates.x !== undefined) this._x = updates.x;          // clearable: null clears
if (updates.y !== undefined) this._y = updates.y ?? DEFAULT;// defaulted: null → default
Never re-drop the null
A field that is neither clearable nor ?? DEFAULT-guarded will now receive null where it used to receive nothing — a latent bug the old drop-the-null behavior hid. Fix the engine merge; don't strip the null back out.
